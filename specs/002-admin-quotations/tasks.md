## Formato y convenciones

`- [ ] Txxx [P?] [Fase] Descripción con ruta · Verifica: … · Depende de: … · Agente: …`

- **[P]**: se puede hacer en paralelo (archivos distintos, sin dependencia pendiente).
- **Etiqueta de fase** `[F1]` … `[F5a]`: reemplaza a `[US#]` de la plantilla porque el propietario pidió organizar por fases entregables. Relación con las historias de la spec: F1 = Historia 5 (+ listado); F2 = Historia 6; F3 = Historias 1, 2 y 3; F4 = Historias 4 y 8; F5a = Historia 7 (aceptación); F5b = Historia 7 (proyecto), **bloqueada**.
- **Migraciones**: una por fase, con los nombres del plan: `supabase/migrations/<MARCA>_cotizaciones_fundacion.sql` (F1), `<MARCA>_catalogo_servicios.sql` (F2), `<MARCA>_cotizaciones_borradores.sql` (F3), `<MARCA>_cotizaciones_emision.sql` (F4) y `<MARCA>_cotizaciones_aceptacion.sql` (F5a). `<MARCA>` es una marca de tiempo posterior a la última migración existente (`20261016120300`) y a la de la fase anterior. Solo hacia adelante: nunca se edita una migración existente; cuando una fase cambia una función de otra, usa `CREATE OR REPLACE FUNCTION` en su propia migración.
- **pgTAP**: `supabase/tests/database/<nombre>.test.sql`, con fixtures `@test.local` y UUID fijos sintéticos. Cada archivo prueba solo lo que su fase crea (`acceso-y-rls.md` §3). Al añadir bloques a un archivo se actualiza su `plan(n)`.
- **Funciones `SECURITY DEFINER`**: `SET search_path = public, pg_temp`, objetos cualificados, `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role` y `GRANT EXECUTE … TO authenticated` solo para las RPC de la lista canónica (`rpc-cotizaciones.md` §0). Primera sentencia de cada RPC: `get_user_type()` distinto de 0 → `COT:SIN_PERMISO`.
- **Volatilidad y bloqueo**: las funciones que escriben son `VOLATILE` y bloquean la fila de la cotización con `SELECT … FOR UPDATE` antes de comprobar nada. `cotizacion_validar` es `STABLE`, solo lee y **no** bloquea filas (`rpc-cotizaciones.md` §1).
- **Versión por fila** (`data-model.md` §3.1): `cotizacion_lineas`, `cotizacion_tramos` y `cotizacion_hitos` llevan su propia `row_version`, que el navegador no escribe. Todo `UPDATE` y todo `DELETE` de esas filas desde la capa de datos lleva `row_version = <versión leída>`; 0 filas afectadas es un conflicto de edición: no se reintenta solo y nunca sobrescribe el cambio de otro administrador.
- **Inmutabilidad por lista blanca**: fuera de borrador, toda columna de `cotizaciones` queda congelada salvo la lista blanca de `ciclo-de-vida.md` §5. La fase que añade columnas las clasifica en su migración y solo amplía la lista con `CREATE OR REPLACE FUNCTION`.
- **Sin exenciones**: ninguna tarea introduce una variable de sesión, un parámetro del cliente, una exención por rol ni un trigger desactivado para saltarse una validación. Las vías especiales (copias de revisión y de duplicado) se apoyan en columnas que el navegador no puede escribir, y el trigger las valida (`acceso-y-rls.md` §1.1).
- **Errores exactos y auditoría sin datos personales**: toda prueba de error usa `throws_ok(…, 'P0001', 'COT:<CODIGO>')`, con el SQLSTATE y el mensaje exactos; los errores de privilegio usan `42501`. El `detalle` de un evento solo admite el esquema estricto de `data-model.md` §2.9 (claves, tipo, formato y tamaño; sin importes ni datos personales).
- **Tipos generados**: `src/integrations/supabase/types.ts` se regenera contra una base local desechable (R-21), con `postgres-meta` v0.100.0, solo el esquema `public` y PostgREST 14.4; si el archivo está desfasado respecto al esquema existente, primero se pone al día en su propio commit y después se añade lo de la fase (T007); nunca a mano ni contra producción.
- **Gate común** (cierra cada fase): `npm run lint && npx tsc -p tsconfig.app.json --noEmit && npm test && npm run build`, más `supabase test db`. Requiere Docker; si no está disponible, la tarea se informa como **bloqueada**, no como hecha. Localmente `supabase test db` puede sustituirse por la verificación equivalente: una base PostgreSQL desechable con la imagen de Supabase en Docker, publicada solo en `127.0.0.1`, con las migraciones aplicadas en orden (una transacción por archivo), un arranque de compatibilidad del esquema `auth` y `pg_prove` sobre `supabase/tests/database/`. No es idéntica al entorno completo de la CLI de Supabase (sin GoTrue, PostgREST ni `seed.sql`) y **no sustituye a CI**: `db-tests.yml` sigue ejecutando `supabase test db`, y esa ejecución oficial queda pendiente hasta que CI corra.
- **Repo público**: solo datos sintéticos; sin secretos, rutas absolutas, ids de proyecto Supabase ni documentación privada.
- **Producción**: solo el **Propietario**. Las tareas marcadas «Propietario» no las ejecuta quien implementa. Las migraciones se aplican **en orden de fase** y cada una con la **autorización expresa y separada** del propietario: la de una fase no cubre la siguiente, no se aplica una migración si la de la fase anterior no está aplicada y verificada, y nunca se agrupan dos fases en una misma aplicación.
- **Prohibido en todas las fases** (no se generan tareas): descuentos, impuestos, pasarelas de pago, facturación, PDF, correo, Edge Functions, Storage (salvo DA-02, que no está aprobada), dependencias nuevas, cambios en CI o `.claude/settings.json`, rutas distintas de las tres autorizadas.

```text
F1 (T001–T026) ─► F2 (T027–T046) ─► F3 (T047–T080) ─► F4 (T081–T117) ─► F5a (T118–T147) ─╳─► F5b
```

- Cada fase es **un PR y una migración**, y termina en su punto de control. La fase siguiente no empieza hasta cerrar la anterior.

- Las tareas de pruebas con vectores (T032, T060, T097, T099, T135) van **antes** que su implementación.

- Base de datos: migración (varias partes del mismo archivo, en serie) → pgTAP (en serie, mismo archivo) → `supabase test db` + tipos → capa de datos → componentes → pantallas → pruebas de pantalla → cierre.
